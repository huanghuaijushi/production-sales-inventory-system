# Web 端 UI / UX 优化方案

> 分支：`feat/ui-ux-optimization`
> 创建日期：2026-05-15
> 视角：从经营者每日实际工作流程出发，而不是从数据库表结构出发。

---

## 0. 核心判断

**当前系统是按数据库表平铺出来的目录，不是按用户的工作流程组织的产品。**

用户打开系统问的是："今天我需要处理什么？"
当前系统回答的是："这是我们能跟踪的所有数据。"

这是两个完全不同的问题。本次优化要把答案对齐到第一个问题。

---

## 1. 登录页（LoginView）

### 问题

| 序号 | 问题 | 影响 |
|---|---|---|
| 1.1 | 左侧四条 marketing 风格的功能列表 | 用户已经决定登录，这些信息是噪音 |
| 1.2 | "Admin Console" 英文 eyebrow 混在中文页面里 | 身份不清，不是国际化是混乱 |
| 1.3 | "还没有管理员账号？创建账号"自助注册入口 | 内部系统不应公开注册；安全和品控风险 |
| 1.4 | 系统描述段落过长 | 用户每天看一次，文案被读完后就成了视觉障碍 |

### 修改

- 删掉左侧 `login-feature-list`（产销存数据联动等 4 条）。
- 删掉 `login-header__eyebrow` 的 "Admin Console" 文案。
- 删掉 `auth-switch` 块（连同 `/register` 路由）。
- 左侧描述段从两行缩成一句话品牌定位。
- 保留：左右分栏结构、表单本身、记住登录、错误提示。

---

## 2. 首页 / Dashboard

### 问题

| 序号 | 问题 | 影响 |
|---|---|---|
| 2.1 | 利润分析（毛利率）被放在页面最下方，需要滚动才能看到 | 经营者最关心的信号被埋藏 |
| 2.2 | 顶部 4 个指标（今日入库/出库/损耗/待发货）回答的是"发生了什么" | 用户问的是"哪些需要我处理"，没人回答 |
| 2.3 | "原料监控"和"成品监控"两个图表模块视觉结构完全一样 | 必须读标题才能区分，复制粘贴感 |
| 2.4 | 图表趋势线是 CSS `clip-path` 裁出来的假曲线 | 是剧场不是产品；数据没接通就显示假图比不显示更糟 |
| 2.5 | 6 个快捷操作和 6 个指标卡并排同一视觉层级 | 用户失去主次锚点 |

### 修改

按"用户每天打开首页要看什么"重新组织：

1. **第一屏：今天的工作面板**
   - 待发货订单数（红色提醒）
   - 库存预警 SKU 数
   - 今日毛利率（绿色 / 红色）
   - 三个数都可以一键跳转到对应处理页

2. **第二屏：快捷操作**
   - 6 个按钮独占一行，明确是"动作"区
   - 不再和数据指标混排

3. **第三屏：趋势与分析（可滚动）**
   - 真实图表，未接入前显示"暂无足够数据"
   - 原料和成品监控合并成一个 Tab 切换组件，不要两个并排
   - 删除所有 CSS clip-path 假折线

## 3. 侧边菜单（AuthenticatedLayout）

### 问题

| 序号 | 问题 | 影响 |
|---|---|---|
| 3.1 | 12 个菜单项平铺无分组 | 超出心智模型容量 |
| 3.2 | "库存产品"和"商品管理"并列且名字接近 | 用户分不清谁是谁，来自数据库表名而非业务语言 |
| 3.3 | "生产计划"和"生产配置"独立两个一级菜单 | 用户脑子里只有"生产"一件事 |
| 3.4 | 用户/角色/权限三项和采购/销售同级 | 配置型功能侵占运营型菜单空间 |
| 3.5 | 侧边栏底部 📦 emoji 装饰 | B2B 工具不需要消费品的可爱感 |

### 修改

新菜单结构（一级菜单压缩到 6-7 项）：

```
首页
库存          → 整合现"库存管理"+"库存产品"
采购
生产          → 整合现"生产计划"+"生产配置"为内部 Tab
销售
供应商
─────────
系统设置      → 折叠用户 / 角色 / 权限
```

- 用一条分割线把"运营"和"系统设置"区分开。
- 删掉侧边栏底部的 📦 emoji。

## 4. 横跨所有页面的系统性问题

### 4.1 原生浏览器弹窗破坏品牌感

**现状：** 10+ 处使用 `window.confirm()` 和 `window.alert()`：

- `PurchaseManagementView`：确认入库、取消采购单
- `SalesManagementView`：发货出库、取消订单、确认导入批次
- `ProductionPlanView`：取消工单
- `ProductionConfigView`：删除配方、删除工序
- `SupplierManagementView`：删除供应商、删除供货规则
- `SysUserManagementView`：禁用用户

**修改：** 做一个统一的 `ConfirmDialog` 组件
- 标题 + 正文 + 取消 / 确认两按钮
- 支持 `danger` 模式（红色确认按钮）
- 全局调用 `useConfirm()` composable
- 替换所有 `window.confirm` 调用

### 4.2 页面标题三重冗余

**现状：** 用户打开"库存管理"，屏幕上同时出现：
1. 侧边栏 nav 高亮 "库存管理"
2. 顶部面包屑 "库存管理 / 库存总览"
3. 页面内 `page-eyebrow` "库存管理" + `<h1>` "库存总览" + 一段说明文案

**修改：**
- 删掉所有页面的 `page-eyebrow` 元素
- 删掉每页开头的 marketing 风格说明段
- 每页只保留一个 `<h1>` 作为页面主标题（且与面包屑 sub 一致）

### 4.3 没有统一的消息反馈系统

**现状：** 每个页面用 `<p v-if="message" class="operation-message">` 自己实现，位置不固定、不自动消失、成功 / 错误共用样式。

**修改：** 全局 Toast 组件
- 固定位置（建议顶部居中）
- 3 秒自动消失
- 三态：success / error / warning
- 全局 `toast.success()` / `toast.error()` 调用
- 替换所有 `operation-message` 用法

### 4.4 空状态看起来像故障

**现状：** 列表为空时只显示一行表格 "暂无销售单 / 暂无采购单 / 暂无出入库记录"。新租户第一次进入看起来像系统装坏了。

**修改：** 每个列表的空状态组件包含：
- 图示
- 一句话说明这里会出现什么
- 一个主操作 CTA（如"新增第一张采购单"）

### 4.5 销售页两个搜索框

**现状：** `SalesManagementView` 顶部 header-search 一个搜索框，下方 filter-panel 又一个搜索框，绑定同一个 `filters.query`。

**修改：** 删掉顶部 header-search，只保留 filter-panel 里的搜索（带状态筛选）。其他页面同样原则：搜索入口唯一。

### 4.6 状态色码体系各自为政

**现状：** 每个模块自己定义 `status-pill--pending` 等 CSS class，颜色不统一。

- 销售：PENDING / SHIPPED / COMPLETED / CANCELLED
- 采购：DRAFT / PENDING_INBOUND / INBOUNDED / CANCELLED
- 库存流水：IN / OUT
- 生产工单：独立一套

**修改：** 抽象 5 种业务状态语义和对应颜色：

| 语义 | 颜色基调 | 对应业务状态举例 |
|---|---|---|
| 进行中 | 蓝 | SHIPPED、PENDING_INBOUND |
| 待处理 | 橙 | PENDING、DRAFT |
| 已完成 | 绿 | COMPLETED、INBOUNDED |
| 已取消 | 灰 | CANCELLED |
| 异常 | 红 | 损耗、库存预警 |

各模块状态枚举映射到这 5 个语义，统一一套 `StatusPill` 组件。

### 4.7 自助注册管理员账号是安全隐患

**现状：** 登录页有"创建账号"链接指向 `/register`，公开可注册管理员账号。

**修改：**
- 删除 `/register` 路由和 `RegisterView.vue`
- 删除登录页的 `auth-switch` 块
- 新管理员通过现有管理员在"用户管理"中邀请创建

### 4.8 没有键盘快捷键

**现状：** 仓库、销售、运营每天用此系统几小时，但完全无键盘支持。

**修改（最小版）：**
- `/` 聚焦全局搜索
- `Esc` 关闭所有弹窗
- `Cmd / Ctrl + Enter` 在表单内提交
- `Cmd / Ctrl + K` 召唤全局搜索面板（可选）

### 4.9 模态弹窗状态散落

**现状：** `InventoryView` 里有 `modalOpen` / `stockEditModalOpen` / `lossModalOpen` / `checkModalOpen` 等多个独立 ref，每个弹窗一套打开 / 关闭逻辑。

**修改：** 抽象 `useModal` composable 或 Pinia store，集中管理弹窗栈。可同时解决：
- 路由切换时自动关闭所有弹窗
- 同时只能开一个弹窗
- 统一动画与 backdrop 行为

## 5. 实施优先级

按"用户能立刻感受到品质提升"排序。

### 第一批：精致感（一周内可见效）

1. **替换所有原生 `window.confirm` 为 `ConfirmDialog` 组件** — 修完整个系统的专业感立刻上一个台阶
2. **删除页面三重标题冗余** — 每个页面都立刻变得清爽
3. **全局 Toast 系统替换 `operation-message`** — 操作反馈终于一致
4. **空状态组件** — 新用户首次体验不再像故障

### 第二批：信息架构（两周）

5. **侧边菜单 12 → 6/7 项重组** — 心智模型可建立
6. **首页重构（关注 → 操作 → 趋势 三层）** — 真正回答"今天要做什么"
7. **删除 `/register` 路由 + 登录页瘦身** — 安全风险消除、品牌清晰

### 第三批：系统化（持续）

8. **统一 5 种业务状态语义和色码** — 跨模块认知成本下降
9. **统一搜索入口（去除每页重复搜索框）** — 操作肌肉记忆形成
10. **键盘快捷键最小集** — B2B 工具该有的样子
11. **`useModal` composable 抽象** — 技术债清理

---

## 6. 不做什么（保留项）

避免本次优化范围蔓延：

- **不动后端 API 和数据结构**——纯前端体验层优化
- **不改业务流程**——审批、状态机、权限规则保持原样
- **不重写 Element Plus**——继续基于现有 CSS 和组件
- **不做移动端响应式**——移动场景由独立 App 承担
- **不做主题切换 / 暗色模式**——超出范围

---

## 7. 验收标准

每一项改动验收时问三个问题：

1. **用户每天打开是否更快地知道该做什么？**
2. **同一条信息是否只出现一次？**
3. **操作完成后的反馈是否在同一个位置、同一种样式？**

任何一个回答"否"的改动，需要继续打磨。
